# ADR-0004: Реестр провайдеров и capability-модель

Статус: accepted · Дата: 2026-11-16

## Контекст

Провайдеров много и они разные: биржи, брокеры, источники данных, LLM,
decision-модели, нотификаторы. Нужна замена без правки ядра и без
`if provider == "..."` по коду.

## Решение

- Провайдер — отдельный Go-модуль, реализующий порт (`Venue`, `MarketData`,
  `LLM`, `Decision`, `Notifier`).
- Каждый объявляет `Descriptor` с `Capabilities` (`VenueCaps`, `LLMCaps` и т.д.),
  схемой конфига (`ConfigField`) и явными деградациями.
- Возможность считается как `ProviderDescriptor ∩ AccountContext ∩
  InstrumentDescriptor` и даёт один из четырёх исходов: `NATIVE | EMULATED |
  DEGRADED | UNSUPPORTED` с reason-code. Отказ — до отправки ордера.
- Реестр (`providers/registry`) собирается в composition root; фабрика получает
  `Deps` (креды, HTTP-клиент, часы, логгер) и не читает env/глобалы.
- Правила вендора (`CanSubmit/CanAmend/CanCancel`, buying power, fees) — объект
  `VenuePolicy`, который возвращает адаптер, а не `if` в риск-модуле.
- Conformance-набор (`core/porttest`) обязателен для попадания в релиз.

## Последствия

- Новый вендор = новый модуль + descriptor + тесты; ядро и клиенты не меняются.
- UI строит формы подключения из `ConfigField`, а матрицу возможностей — из
  `Capabilities`.
- Агент-паки объявляют `requires`/`appliesTo`; несовместимые не загружаются с
  понятной причиной.
- Ограничение: в v1 провайдеры компилируются в бинарник (Go plugins хрупки).
  Out-of-process паки по gRPC — v2.

## Альтернативы

- **Go `plugin`**: только Linux/macOS, жёсткая привязка версий, хрупко.
- **Отдельный процесс на каждый провайдер**: гибко, но дорого по ресурсам и
  сложно для локального desktop; оставлено для v2.
- **Универсальный CCXT-адаптер на всё**: удобно, но теряются вендорские фичи
  (user data stream, reduce-only, funding), которые и есть дифференциатор.
