# ADR-0006: Decision-модели — первоклассный провайдер

Статус: accepted · Дата: 2026-11-16

## Контекст

Ориентиры владельца — Drex Max v1.1 (Nace.AI) и Jev (TypeSafe) — это не чат-LLM,
а decision-модели: на вход `state` + именованные вопросы с вариантами, на выход
вероятность каждого варианта за один forward pass, без генерации текста. Такие
модели дешевле, быстрее и калиброваннее для bounded-решений («buy/sell/hold»,
«approve/reject», «какой вендор»).

Если смоделировать их как «LLM с JSON-промптом», теряются их главные свойства:
закрытый набор вариантов, вероятности, калибровка, стоимость.

## Решение

Ввести отдельный порт `Decision` и отдельный тип провайдера `decision`:

```go
type Decision interface {
    Descriptor() Descriptor
    Info(ctx) (DecisionInfo, error)
    Decide(ctx, DecisionRequest) (DecisionResponse, error)
}
```

Поддерживаются несколько вопросов на один `state`, изображения (графики,
скриншоты), батчинг, идемпотентный ключ, таймаут и учёт стоимости. Адаптеры
`decision-drex` и `decision-jev` используют один код с разными профилями
(base URL, авторизация, модель), т.к. API wire-compatible.

Политика поверх (не внутри) провайдера: порог уверенности, fallback, «abstain»,
второй голос, логирование калибровки (Brier/ECE), запрет входа при недоступности
провайдера при сохранённой возможности выхода.

## Последствия

- Агент может быть «decision-агентом» без промптов и без генерации текста:
  дешевле, быстрее, воспроизводимее.
- Один и тот же `Proposal`-контракт для LLM и decision-моделей: аггрегатор и
  RiskGate не различают источник.
- Появляется измеряемая калибровка и естественный A/B между моделями.
- Нужен отдельный набор conformance-тестов (невалидные ответы, изображения,
  таймауты, стоимость).

## Альтернативы

- **Только LLM**: дороже, медленнее, хуже калибровка на bounded-задачах.
- **Только decision-модели**: не покрывает генерацию объяснений и research-задачи.
- **Смешать в одном порте `LLM`**: размывает контракт и типы; отклонено.
