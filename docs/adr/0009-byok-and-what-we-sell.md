# ADR-0009: Два режима оплаты ИИ — BYOK и провайдер LV24

Статус: accepted (владелец, 2026-11-16) в части двух режимов; цены и предмет продажи —
открыты до M5 · Редакция 2 · Источник: `docs/review/01-findings.md` F-02, F-03, F-09, F-20

Редакция 1 (proposed, коммит `f6dda7a`) предлагала только BYOK и запрет перепродажи
токенов. Владелец выбрал два режима; редакция 1 заменена этой до принятия.

Уточняет (amends) [ADR-0007](0007-license-and-stores.md): лицензия MIT и запрет
AGPL/GPL остаются в силе; меняется место исходников платной сборки и то, что
считается источником выручки.

## Контекст

В спеке v0.1 нет бизнес-модели. Единственное упоминание продажи — мобильное
приложение (ADR-0007). При этом:

- значения по умолчанию для LLM-бюджета дают до $300 в месяц на пользователя
  (`02-monorepo.md:183`); при подписке около $10 это убыток, если платим мы и не
  берём за это отдельно;
- мобильное приложение по плану лежит в публичном MIT-репозитории
  (`02-monorepo.md:83`): его можно собрать бесплатно;
- App Store требует, чтобы приложения для торговли подавала организация,
  оказывающая финансовые услуги (guidelines 3.2.1(viii), 5.1.1(ix)), а разблокировка
  функций шла через встроенные покупки (3.1.1);
- у владельца есть собственный OpenAI-совместимый шлюз `lv24/main/ai-gateway`
  с леджером использования. По его README он не выпущен и не развёрнут, отдаёт
  `chat/completions` и не имеет эндпоинта decision-моделей (`/v1/systemone`).

## Решение

Пользователь выбирает один из двух режимов на каждое подключение ИИ.

### Режим A — свои подписки (BYOK)

1. Пользователь вводит собственный API-ключ вендора. Ключ хранится в keychain на
   его машине; мы его не видим и ничего не проксируем.
2. Вход через подписку вендора (OAuth вместо ключа) — допустимый способ
   авторизации, но только для вендоров, чьи условия разрешают использовать
   подписку в стороннем приложении. Условия не проверены; до проверки по каждому
   вендору в продукте доступны только API-ключи.
3. Бюджеты в приложении в этом режиме — защита пользователя от собственных
   расходов, а не наш биллинг.

### Режим B — провайдер LV24

4. Пользователь авторизуется в LV24 и платит нам; запросы идут через
   `lv24/main/ai-gateway`. В ядре это обычный провайдер из реестра
   (`llm-openaicompat` с базовым адресом LV24, позже — `decision-lv24`), ядро и
   клиенты не меняются.
5. Режим B появляется не раньше M5: шлюз дорабатывается отдельно, в проекте `lv24`.
   Клин и v1 до M5 работают только в режиме A.
6. Режим B — основной кандидат на источник выручки. Цена, наценка и форма
   (подписка, пакеты, оплата по факту) определяются на M5.

### Общее

7. **Гейт «только на сигналы входа» — режим по умолчанию.** Опрос модели на каждой
   свече включается явно, с показом прогноза расходов за месяц.
8. **Цены хранятся за 1B токенов decimal-строкой**; расчёт покрыт тестом на примере
   из документации вендора.
9. **Ключи бирж не покидают машину пользователя ни в одном режиме.** Провайдер LV24
   получает только запросы к моделям.
10. **Исходники платной store-сборки** — в отдельном приватном репозитории, если
    владелец не выберет осознанно модель «открытый код, платят за удобство».
11. **Мобильное приложение не планируется как первый источник выручки** и не
    начинается без решения по сторам (ADR-0011).

## Последствия

- В режиме A себестоимость ИИ для нас равна нулю.
- Режим B превращает нас в поставщика услуги: появляются аккаунты, биллинг,
  поддержка платежей и обработка персональных данных пользователей из разных
  стран. Это отдельные обязательства, которые оформляются до запуска режима B.
- В режиме B в шлюз уходит state запроса: рыночные данные и, возможно, размер
  позиции. Это нужно прямо сказать пользователю; README шлюза заявляет, что запросы
  и ответы не хранятся.
- Наценка на токены decision-моделей почти ничего не даёт: при расходе $0.65 в
  месяц на пользователя (`docs/review/01-findings.md §3`) наценка 30% приносит
  $0.20. Выручка режима B возможна только как фиксированная плата за доступ либо
  на LLM-трафике, где суммы на порядки больше.
- Перепродажа доступа к моделям должна быть разрешена условиями каждого вендора
  (Nace, TypeSafe, поставщики LLM). Условия не проверены.
- Продажа пакетов или подписки LV24 внутри мобильного приложения подпадает под
  обязательные встроенные покупки стора и его комиссию.
- Чтобы режим B покрыл клин, шлюзу нужен эндпоинт decision-моделей; сейчас его нет.
- Регистрация разработчика в App Store — платная; решение о ней принимает владелец
  вместе с решением о mobile.

## Что нужно проверить до M5

| Что | Зачем |
|---|---|
| Условия вендоров о входе через подписку в стороннем приложении | режим A, п. 2 |
| Условия вендоров о перепродаже доступа | режим B |
| Требования к обработке персональных данных в РБ и в странах пользователей | режим B |
| Способ приёма платежей из разных стран юрлицом из РБ | режим B |

## Альтернативы

- **Только BYOK** (редакция 1). Отклонено владельцем: нет собственного источника
  выручки и выше порог входа.
- **Только провайдер LV24.** Отклонено: шлюз не выпущен, клин ждать его не может;
  часть пользователей не станет отправлять запросы через посредника.
- **Включить ИИ в единую подписку без учёта расхода.** Отклонено: расход на
  пользователя не ограничен сверху.
- **Сразу платная мобилка.** Отклонено: ей нечем управлять до M3, и она упирается в
  правила сторов.
